# Техническое задание
## Исследование и разработка AI-pipeline для анализа повреждений автомобилей по изображениям

---

## 1. Фокус исследования

**Основная цель:** Исследовать возможность использования мультимодальной AI-модели (Claude Vision) для распознавания видимых повреждений автомобилей и оценить качество этого подхода на объективном benchmark.

**Что это НЕ:**
- Не основная задача: создание полнофункционального приложения
- Не основная задача: интеграция с реальными ценовыми API
- Не основная задача: красивый интерфейс или production-готовое решение

**Telegram-бот:** Минимальный интерфейс исключительно для демонстрации работы pipeline. Не является объектом исследования.

**Расчет стоимости:** Демонстрационная функция (справочник типичных цен в JSON). Не основная исследовательская задача.

**ВАЖНО:** Результаты этого исследования имеют предварительный и исследовательский характер. Выборка из 40 примеров (16 dev + 24 test) является пилотной для короткой практики. Для робастных выводов требуется расширенная валидация на большей выборке.

## 2. Датасет: SYNDCAR

**Почему не CarDD.** Изначально планировался CarDD. Его правообладатель (PIC Lab, CAS) требует предварительного согласия и запрещает передавать снимки третьим лицам, включая внешний AI-сервис, без разрешения. Запрос был отправлен, ответа за время практики не получено. Использовать CarDD без разрешения нельзя, поэтому датасет заменён. Проверенный запасной вариант Car Parts and Car Damages (Humans in the Loop, CC0) не подошёл: в доступных архивах оказалась только часть с разметкой деталей, без разметки повреждений.

**Источник:** SYNDCAR: Synthetic Vehicle Damage Detection and Parts Segmentation Dataset. Digital Transformation CoLAB (DTx CoLAB) и Universidade do Minho, Mendeley Data, V1, 2025. DOI: 10.17632/hzpj48krdt.1, https://data.mendeley.com/datasets/hzpj48krdt/1

**Лицензия:** CC BY 4.0. Разрешает использование, в том числе отправку снимков во внешний AI-сервис, и распространение производных данных при условии указания авторов. Ссылка на датасет приводится в README и в отчёте.

**Состав:**
- 245 снимков, сделанных пятью разными устройствами; имя файла начинается с идентификатора устройства
- повреждения: 4 класса, размечены рамками (формат YOLO)
- детали: 28 классов, размечены полигонами на тех же снимках
- официального разбиения на части нет

**Что берём из разметки:**
- damage_type и рамка повреждения — из разметки повреждений
- part — определяется автоматически: деталь, полигон которой покрывает наибольшую долю рамки повреждения (не менее 10%). Разметчик проверяет её и исправляет при необходимости; если подходящей детали нет, заполняет вручную

**Что размечаем вручную:** `severity`, `action` и проверка `part`

**Соответствие классов** (выполняет scripts/convert_syndcar.py, фактическое соответствие сохраняется в отчёт конвертации):

| SYNDCAR | Проект |
|---|---|
| broken glass | glass_shatter |
| broken lights | lamp_broken |
| cracks | crack |
| scratches | scratch |

Детали: двери → door; боковые окна → window; лобовое и заднее стекло → windshield; фары и фонари → light; четверти кузова → fender; передняя и задняя панели → bumper; зеркала → mirror; колёса → wheel; крыша, пороги, номерной знак → other.

**Разметка 40 примеров:**
- Первый разработчик: размечает все 40 примеров (16 dev + 24 test)
- Второй разработчик: независимо проверяет 100% примеров для валидации разметки
- При несогласии: консенсус через обсуждение и документирование решения

## 4. Входные и выходные данные

**Benchmark (одно изображение):**
- Входные данные: одно изображение из SYNDCAR
- Формат: JPEG или PNG
- Обработка: независимый анализ каждого снимка

**Демонстрационный сценарий (серия фотографий):**
- Входные данные: 3-10 фотографий одной машины
- Формат: JPEG или PNG
- Размер: каждое < 5MB, всего < 10MB
- Обработка: анализ и объединение результатов

**Выходные данные (JSON):**
```
damages: array
  - damage_type: enum (glass_shatter, lamp_broken, crack, scratch)
  - part: enum (bumper, door, light, window, windshield, hood, fender, mirror, wheel, other)
  - severity: enum (minor, moderate, severe)
  - action: enum (repair, replacement)
  - confidence: number 0-1
  - description: string
  - bounding_box: [x, y, w, h] — обязательное поле, координаты нормированы к [0, 1] относительно ширины и высоты снимка

overall_score: number 0-100
```

Нормированные координаты используются потому, что API может уменьшать большие изображения перед анализом, и пиксельные координаты модели были бы неоднозначны. Эталонные рамки (пиксели, формат COCO после конвертации) нормируются по размеру изображения при оценке.

Снимки SYNDCAR сделаны в высоком разрешении. Перед отправкой в модель снимки, у которых длинная сторона больше 1568 пикселей или размер больше 4,5 МБ, уменьшаются с сохранением пропорций (лимит API — 5 МБ на изображение). Нормированные рамки при этом остаются верными.

## 5. AI-Pipeline

**Шаг 1:** Загрузка и валидация изображения (формат, размер, разрешение)

**Шаг 2:** Конвертирование в base64

**Шаг 3:** Формирование промпта с JSON Schema и инструкциями

**Шаг 4:** Вызов Claude API. Модель: Claude Opus 5.5, API-идентификатор `claude-opus-5-5` (проверено по официальной таблице моделей Anthropic, platform.claude.com/docs, раздел «Models overview»; идентификатор является закреплённым снапшотом модели, что обеспечивает воспроизводимость). Идентификатор задаётся в конфигурации и записывается в отчёт benchmark.

**Шаг 5:** Парсинг JSON ответа (десериализация Jackson)

**Шаг 6:** Явная проверка формата ответа (класс ResponseFormatValidator, вызывается сразу после десериализации)

**Шаг 7:** Retry механизм (max 3 попытки при ошибке валидации)

**Шаг 8:** Fallback результат если 3 retry не помогли

**Шаг 9:** Для демо сценария - merging результатов из нескольких фото

## 6. JSON Schema и валидация

**Как запускается проверка ответа:**
1. Jackson десериализует текст ответа в объект. Этот шаг проверяет только, что ответ является JSON нужной структуры; значения полей на этом шаге не проверяются.
2. Сразу после этого анализатор явно вызывает ResponseFormatValidator. Аннотации валидации не используются, поэтому проверка не зависит от настройки фреймворка и не может быть случайно пропущена.

**Что проверяет ResponseFormatValidator:**
- наличие overall_score в диапазоне 0–100 и массива damages (пустой массив допустим — это «повреждений не найдено»);
- для каждого повреждения: damage_type, part, severity, action — из допустимых списков; confidence в диапазоне 0–1;
- bounding_box: ровно 4 числа в [0, 1], ширина и высота > 0, рамка не выходит за пределы изображения.

При нарушении выполняется повторный запрос; в повторный промпт добавляется список найденных нарушений. После 3 неудачных попыток возвращается fallback-ответ со status = "error".

**Различие успешного анализа и JSON об ошибке:**

Успешный анализ:
```json
{
  "status": "success",
  "damages": [...],
  "overall_score": 65
}
```

Ошибка анализа (корректный JSON):
```json
{
  "status": "error",
  "damages": [],
  "overall_score": 0,
  "error_message": "Could not analyze image after 3 retries. Please try with clearer photos."
}
```

Оба варианта — корректные JSON-ответы, но с разным значением `status`. Пустой список damages при status = "success" означает «повреждений не найдено», при status = "error" — «анализ не удался». HTTP-статус: 200 для success, 502 для error, 400 для некорректного входа.

## 7. Сопоставление предсказаний с эталоном

**Порог:** один, IoU ≥ 0.5 (стандартный порог обнаружения объектов, PASCAL VOC). Порог фиксируется до экспериментов и не меняется после просмотра результатов.

`IoU = площадь пересечения / площадь объединения` (обе рамки в нормированных координатах).

**Правило «одно предсказание — одно эталонное повреждение»:**
1. Сопоставление выполняется внутри каждого изображения, без учёта типа повреждения (тип оценивается отдельно, см. раздел 10).
2. Предсказания обрабатываются в порядке убывания confidence.
3. Каждое предсказание сопоставляется с ещё не занятым эталонным повреждением с максимальным IoU, если этот IoU ≥ 0.5.
4. Эталонное повреждение может быть сопоставлено не более чем с одним предсказанием. Повторное предсказание того же повреждения считается ложным срабатыванием (FP).
5. Несопоставленные предсказания — FP, несопоставленные эталонные повреждения — FN.
6. Если для изображения pipeline вернул status = "error" или ответа нет, все эталонные повреждения этого изображения считаются FN; число таких изображений указывается в отчёте отдельно.

**Только для сопоставленных пар оцениваются:** тип повреждения, серьёзность, деталь, действие и уверенность.

**Реализация:** scripts/evaluate.py (функция match_image), покрыта тестами: дубль предсказания, одно предсказание на два эталона, значение ровно на пороге, ошибка pipeline.

**Вспомогательная метрика без локализации:** совпадение набора типов повреждений на уровне изображения. Она приводится отдельно и не называется оценкой обнаружения отдельных повреждений.

## 8. Benchmark: две выборки

**Разбиение.** У SYNDCAR нет официального разбиения, поэтому конвертер один раз делит снимки на два непересекающихся пула примерно пополам, с фиксированным seed = 42: пул для dev и пул для test. Делятся не отдельные снимки, а целые съёмочные дни (дата берётся из имени файла `ID<камера>_<дата>_<время>` или, для камеры ID5, из времени в миллисекундах `ID5_<unix-время>`): снимки одной машины идут сериями с интервалом в секунды и, возможно, сняты несколькими камерами, поэтому одна и та же сцена не должна попасть в оба пула. Состав групп и пулов сохраняется в отчёт конвертации. Из каждого пула стратифицированно по 4 классам повреждений выбираются примеры.

### Dev Set (для tuning промпта)

**Источник:** dev-пул SYNDCAR

**Количество:** 16 примеров (4 × каждый класс повреждений)

**Использование:** 
- Экспериментирование с промптом и инструкциями
- Анализ ошибок
- Определение целевых порогов (на основе фактических результатов)

**Процесс:**
1. Запустить dev set с базовым промптом → фиксируем результаты
2. Анализируем что получилось (например: Recall 82%, Precision 78%, F1 0.76)
3. Улучшаем промпт и повторяем (может быть +3-5%)
4. Фиксируем максимум что реалистично достичь = примерный целевой порог
5. Документируем целевые пороги в файле до запуска test set

**Правило настройки промпта.** Dev и test содержат один и тот же автомобиль, поэтому промпт меняется только в общих аспектах: формат ответа, определения типов повреждений и серьёзности, правила рамок. Сведения, относящиеся к конкретному автомобилю (цвет, расположение повреждений, ракурсы), в промпт не добавляются. Каждая версия промпта фиксируется в журнале изменений (`benchmark/prompt_changelog.md`): номер версии, что изменено, на основании каких ошибок dev.

### Test Set (финальная оценка)

**Источник:** test-пул SYNDCAR

**Количество:** 24 примера (6 × каждый класс повреждений)

**Использование:**
- Окончательная объективная оценка качества
- Вычисление всех метрик
- Проверка достижения целевых порогов

**Процесс:**
1. Не менять промпт (заморожен после dev set)
2. Запустить test set
3. Вычислить метрики
4. Сравнить с целевыми порогами (установленными на dev set)

**Зафиксированные идентификаторы примеров:**
- Полный список примеров для dev и test sets зафиксирован в файле `benchmark/dev_examples.txt` и `benchmark/test_examples.txt` с image_id перед началом экспериментов
- Изменение списков примеров во время работы недопустимо

## 9. Ручная разметка ground truth

### Правила для Part (деталь)

- **Bumper:** передний или задний бампер (передняя и задняя панели)
- **Door:** боковые двери (передние или задние)
- **Light:** фара или задний фонарь
- **Window:** боковые стёкла
- **Windshield:** лобовое или заднее стекло
- **Hood:** капот или крышка багажника
- **Fender:** крыло и четверти кузова (боковые части над колёсами)
- **Mirror:** боковое зеркало
- **Wheel:** колесо или шина
- **Other:** если неясно или комбинация

### Правила для Severity (серьезность)

**Minor (легкое):**
- Мелкие царапины и потертости (< 5 см), не затрагивающие грунт
- Короткие трещины, которые не распространяются

**Moderate (среднее):**
- Длинные или глубокие царапины с повреждением краски
- Треснувшее, но целое стекло или фара

**Severe (серьезное):**
- Разбитое стекло
- Разбитая фара или фонарь
- Трещины, угрожающие целостности детали или безопасности

### Правила для Action (действие)

- **Repair:** Можно отремонтировать (scratch; crack, если деталь не разбита)
- **Replacement:** Нужна замена (glass_shatter, lamp_broken, сильно поврежденные части)

### Процесс разметки

1. Первый разработчик размечает все 40 примеров (severity, action; проверяет автоматически определённую part)
2. Второй разработчик независимо проверяет все 40 примеров
3. При несогласии (разметка не совпадает) - консенсус через обсуждение
4. Все решения документируются

## 10. Метрики качества

### Метрика 1: Recall (полнота обнаружения)

`Recall = TP / (TP + FN) * 100`

где TP = сопоставленные пары (IoU ≥ 0.5, раздел 7), FN = эталонные повреждения без пары

### Метрика 2: Precision (точность обнаружений)

`Precision = TP / (TP + FP) * 100`

где FP = предсказания без пары (включая повторные предсказания одного повреждения)

### Метрика 3: F1-score (классификация типа)

`F1 = 2 * (Precision * Recall) / (Precision + Recall)`

Для каждого damage_type отдельно, результат — среднее по классам (macro-F1). Для класса c: TP — сопоставленная пара, где и эталон, и предсказание имеют тип c; FP — предсказание типа c без пары или в паре с эталоном другого типа; FN — эталон типа c без пары или в паре с предсказанием другого типа.

### Метрика 4: Severity Accuracy (точное совпадение серьезности)

`Accuracy = (точные совпадения severity) / (всего сопоставленных предсказаний) * 100`

Оценивается только для предсказаний которые прошли IoU matching.

Confusion matrix severity для анализа ошибок.

### Метрика 5: Confidence Calibration (Brier Score)

`Brier Score = mean((predicted_confidence - actual_correctness)^2)`

где actual_correctness = 1, если в сопоставленной паре тип повреждения предсказан верно, иначе 0. Считается только по сопоставленным парам.

Целевой порог устанавливается по результатам dev set (раздел 11).

Вспомогательная таблица калибровки по диапазонам confidence.

## 11. Установление целевых порогов

**ДО запуска test set:**

1. На основе dev set результатов фиксируем целевые пороги
2. Пороги документируются в файле `benchmark/target_thresholds.json`
3. Целевые пороги должны быть реалистичны (не выше максимума что получилось на dev set + 2-3%)

**После запуска test set:**

4. Если test set результаты >= целевых порогов → MVP соответствует критериям
5. Если test set результаты < целевых порогов → это не означает невыполнение, если:
   - Эксперимент проведен корректно (правильные данные, логика, без ошибок)
   - Результаты объяснены (lighting issues, model limitations, dataset specifics)
   - Error analysis задокументирован

**Критерий успеха: корректное проведение исследования и честная оценка результатов, не просто достижение произвольных порогов.**

## 12. Два сценария использования

### Сценарий А: Benchmark (основное исследование)

- **Входные данные:** одно изображение из SYNDCAR (не серия)

**Сценарии используют разные методики. Benchmark НЕ объединяет результаты нескольких фото.**

## 13. Ограничения

- Пилотная выборка (40 примеров); результаты имеют исследовательский характер, для робастных выводов требуется расширенная валидация
- SYNDCAR — синтетический датасет: повреждения не получены в реальных ДТП. Результаты на нём хуже переносятся на реальные случаи, это указывается в выводах
- Все снимки датасета — один и тот же автомобиль. Результат показывает качество модели на одном автомобиле с синтетическими повреждениями и не переносится автоматически на другие автомобили; dev и test не независимы по автомобилю, поэтому настройка промпта ограничена общими правилами (раздел 8)
- Одну и ту же машину снимали сериями кадров, возможно, несколькими устройствами. Чтобы похожие снимки не попали в оба пула, разбиение выполняется по съёмочным дням; если в один день снимали несколько машин, они все попадают в один пул, что лишь уменьшает разнообразие, но не создаёт утечки. Съёмочных дней всего три (17, 18 и 19 сентября 2024), поэтому пулы неравные: dev — 61 снимок (18 и 19 сентября), test — 184 снимка (17 сентября). Визуальная проверка показала, что во все три дня снимался один и тот же автомобиль с разных ракурсов. Поэтому разбиение по дням исключает только почти одинаковые кадры одной серии, но не делает dev и test независимыми: это один автомобиль. Как это учитывается — см. правило настройки промпта (раздел 8) и ограничения (раздел 13)
- На одном снимке в среднем около 5 повреждений, поэтому выборка из 40 снимков содержит порядка 200 размеченных повреждений
- Снимки (до ~32 МБ, около 3264×2448) перед отправкой уменьшаются до 1568 пикселей по длинной стороне; мелкие царапины при этом могут стать хуже видны
- Типов повреждений четыре: вмятины, отдельные сломанные детали и другие виды повреждений не оцениваются
- Автоматически определённая деталь зависит от точности разметки деталей SYNDCAR; поэтому разметчик её проверяет

## 14. План реализации

**Этап 1 (выполнено):** репозиторий, запускаемый Spring Boot, обработка одного изображения, проверка формата ответа, retry/fallback, заглушка модели, тесты, скрипты выборки, разметки, прогона и оценки

**Этап 2 (выполнено):** замена датасета на SYNDCAR: конвертер в COCO с автоматическим определением детали, новые классы, уменьшение больших снимков

**Этап 3:** Конвертация SYNDCAR, фиксация выборки (16 dev + 24 test), разметка dev

**Этап 4:** Прогон dev set с реальной моделью, анализ ошибок, настройка промпта, фиксация порогов

**Этап 5:** Разметка test set, однократный прогон с замороженным промптом, отчёт

## 15. Критерии приёмки MVP

**MVP соответствует критериям если:**
- Benchmark проведен корректно (правильные данные, логика, без ошибок)
- Целевые пороги установлены на основе dev set результатов
- Test set запущен с замороженным промптом
- Все метрики (recall, precision, F1, severity accuracy, calibration) вычислены
- Error analysis задокументирован с объяснением результатов
- Демо-сценарий (серия фото) обрабатывается без сбоев на 10+ запросах
- JSON валиден в 100% случаев
